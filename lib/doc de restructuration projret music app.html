🧠 Notions techniques à maîtriser

Architecture & Design Patterns
  • Clean Architecture : séparation en 3 couches (domain, data, presentation)
  • Repository Pattern : abstraction de la source de données
  • Use Cases : encapsulation des actions métier
  • Dependency Injection : injection des dépendances à travers les couches
  • Data Model / Entity : séparation entre données brutes et objets métier
Gestion d'état
  • Cubit : version simplifiée de Bloc (méthodes → états)
  • Bloc : version complète (événements → états)
  • BlocProvider : enregistrement des Cubits
  • BlocBuilder : reconstruction de l'UI selon l'état
  • BlocListener : réactions aux changements d'état
Firebase
  • Firebase Auth : inscription, connexion, déconnexion
  • Cloud Firestore : lecture/écriture en temps réel
  • Firebase Storage : upload et streaming des fichiers audio
  • Règles de sécurité : mode test puis mode production
Audio
  • just_audio : lecture audio (setUrl, setAsset, play, pause, seek)
  • audio_service : lecture en arrière-plan, notifications
  • Stream de position : pour la barre de progression en temps réel
UI / UX
  • ListView.builder : listes performantes
  • Hero animation : transitions fluides
  • FadeInImage : chargement d'images avec fondu
  • ThemeData : thème global cohérent
  • Mini-player : widget persistant en bas d'écran

4. Logique complète derrière la conception du produit

Pourquoi construire ce projet avec cette architecture ? Voici la logique fondamentale, expliquée point par point.

🎯 Objectif stratégique

Passer du "débutant qui fait fonctionner" au "professionnel qui construit"

La plupart des tutoriels Flutter montrent comment faire une app qui fonctionne. Ce tutoriel montre comment faire une app qui dure. La différence réside dans :

  • La testabilité : le code peut être testé couche par couche.
  • La maintenabilité : un bug dans Firebase ne casse pas l'UI.
  • La scalabilité : on peut ajouter des fonctionnalités sans tout casser.

🏗️ Logique de la Clean Architecture

Pourquoi 3 couches ?
┌─────────────────────────────────────────┐ │ PRESENTATION (UI + Cubit) │ ← Ce que l'utilisateur voit │ - Pages │ │ - Widgets │ │ - Cubits │ └────────────────┬────────────────────────┘ │ dépend de ↓ ┌─────────────────────────────────────────┐ │ DOMAIN (Métier pur) │ ← Règles métier │ - Entités (Song, User) │ │ - Repositories (abstraits) │ │ - Use Cases │ └────────────────┬────────────────────────┘ │ dépend de ↑ ┌─────────────────────────────────────────┐ │ DATA (Implémentation) │ ← Firebase, etc. │ - Data Sources │ │ - Models │ │ - Repository Implementations │ └─────────────────────────────────────────┘
  • Domain : ne dépend de rien. Code pur, testable, indépendant de Firebase.
  • Data : dépend du domain. Contient l'implémentation concrète (Firebase).
  • Presentation : dépend du domain. Affiche l'UI.

Règle d'or : Les dépendances vont toujours vers le domain, jamais l'inverse.

📦 Logique du Repository Pattern

Pourquoi un repository abstrait ?

Le repository abstrait définit ce que l'app peut faire, sans dire comment.

abstract class SongRepository { Future<List<Song>> getSongs(); }

Le Cubit ne connaît que cette interface. Il ne sait pas si les données viennent de Firebase, d'une API locale, ou d'un fichier JSON. Cela permet :

  • De tester le Cubit avec un faux repository.
  • De changer de source de données sans toucher au Cubit.
  • De paralléliser le développement (une équipe fait Firebase, une autre l'UI).

🎛️ Logique de Bloc / Cubit

Pourquoi pas setState ?

setState est parfait pour une petite app. Mais dès que l'app grandit, il devient ingérable :

  • Le code UI et la logique métier se mélangent.
  • Impossible de tester la logique sans lancer l'UI.
  • Les rebuilds sont incontrôlés.

Avec Cubit, la logique est séparée de l'UI. Le Cubit émet des états, l'UI réagit. On peut tester le Cubit sans lancer l'app.

🔥 Logique de Firebase

Pourquoi Firebase ?
  • Firebase Auth : gestion complète de l'authentification (sessions, tokens, sécurité).
  • Firestore : base de données NoSQL temps réel, scalable.
  • Storage : hébergement des fichiers audio et images.
  • Gratuit pour commencer (plan Spark).

Firebase évite d'avoir à coder un backend (Node.js, Django, etc.). L'app parle directement à Firebase.

5. Description du fonctionnement du produit

Voici le parcours utilisateur complet, étape par étape, de l'ouverture de l'app à la lecture d'une chanson.

🔄 Parcours utilisateur complet

Étape 1 – Lancement de l'app
  1. L'utilisateur ouvre l'application.
  2. Le Splash Screen s'affiche pendant 2 secondes.
  3. En arrière-plan, FirebaseAuth.instance.currentUser est vérifié.
  4. Si un utilisateur est connecté → HomePage.
  5. Sinon → SignInPage.
Étape 2 – Inscription / Connexion
  1. L'utilisateur remplit le formulaire d'inscription.
  2. Il clique sur "S'inscrire".
  3. Le AuthCubit appelle signUpWithEmailAndPassword.
  4. Firebase crée un compte utilisateur.
  5. Le nom est enregistré via updateDisplayName.
  6. Redirection vers HomePage.
Étape 3 – Affichage des chansons
  1. Sur HomePage, HomeCubit.loadSongs() est appelé.
  2. Le Cubit appelle GetSongs (use case).
  3. Le use case appelle SongRepository.getSongs().
  4. L'implémentation appelle SongRemoteDataSource (Firestore).
  5. Firestore renvoie les documents de la collection songs.
  6. Chaque document est converti en Song via SongModel.fromJson.
  7. La liste est émise via HomeLoaded(songs).
  8. L'UI affiche les cartes de chansons.
Étape 4 – Lecture d'une chanson
  1. L'utilisateur clique sur une chanson.
  2. Le PlayerCubit.playSong(song) est appelé.
  3. just_audio charge l'URL (Firebase Storage) via setUrl.
  4. La lecture démarre.
  5. Un positionStream met à jour la position en temps réel.
  6. Le mini-player apparaît en bas de l'écran.
  7. La PlayerPage affiche la pochette, le titre, l'artiste, la barre de progression.
Étape 5 – Ajout aux favoris
  1. L'utilisateur clique sur le cœur d'une chanson.
  2. Le FavoritesCubit.addFavorite(song) est appelé.
  3. Le favori est enregistré dans Firestore (collection favorites).
  4. Le cœur devient rouge.
  5. La chanson apparaît dans FavoritesPage.
Étape 6 – Création d'une playlist
  1. L'utilisateur va sur PlaylistsPage.
  2. Il clique sur le FAB (+).
  3. Une boîte de dialogue demande le nom.
  4. Le PlaylistCubit.createPlaylist(nom) est appelé.
  5. La playlist est enregistrée dans Firestore.
  6. Elle apparaît dans la liste.
Étape 7 – Déconnexion
  1. L'utilisateur va sur ProfilePage.
  2. Il clique sur "Déconnexion".
  3. Le AuthCubit.signOut() est appelé.
  4. FirebaseAuth.instance.signOut() est exécuté.
  5. Redirection automatique vers SignInPage (via StreamBuilder).

🔗 Flux de données global

[UI - Page] ↓ (utilisateur clique) [Cubit] ↓ (appelle) [Use Case] ↓ (appelle) [Repository] ↓ (appelle) [Data Source] ↓ (communique avec) [Firebase / Local] ↑ (retourne les données) [Model → Entity] ↑ (converti) [Repository] ↑ (retourne) [Use Case] ↑ (retourne) [Cubit] ↑ (emit State) [UI - BlocBuilder] → Reconstruit l'écran

📊 Points critiques du fonctionnement

⚠️ Attention : Le positionStream de just_audio émet la position à intervalles très courts (toutes les 200ms environ). Si on émet un nouvel état PlayerPlaying à chaque émission, on rebuild l'UI très fréquemment. C'est acceptable pour cet écran, mais il faut en être conscient.
⚠️ Attention : Les règles Firestore en mode test expirent après 30 jours. Il faudra les passer en mode production avec des règles strictes (seul le propriétaire peut lire/écrire ses données).
⚠️ Attention : La lecture en arrière-plan via audio_service nécessite des permissions Android (FOREGROUND_SERVICE, WAKE_LOCK) à ajouter dans AndroidManifest.xml.
